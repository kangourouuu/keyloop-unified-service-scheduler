Unified Service Scheduler design

Keyloop Scenario A, backend only. Approved design plus the KUSS-02 plan, red-team and validation decisions.

A booking gets one active bay and one qualified technician for the whole [start, end) window, or a clear KUSS_* error. PostgreSQL enforces this with three partial EXCLUDE USING gist constraints. The service re-queries free pairs and retries when a concurrent booking wins.

B

Architecture

  • Runtime: Docker Compose (Podman works the same) runs two containers: db (postgres:17, deadlock_timeout=100ms, bound to 127.0.0.1) and app (non-root, prod profile).
  • Observability: Actuator health probes, Micrometer Prometheus meters, Brave tracing for traceId / spanId in MDC, ECS JSON logs in prod.
  • API docs: springdoc OpenAPI at /v3/api-docs and Swagger UI at /swagger-ui.html.
  • Not in V1: Redis, RabbitMQ and WebSocket stay out of the code and out of docker-compose.yml.
C

Data model and constraints

Three partial exclusion constraints on appointment (btree_gist, WHERE status = 'CONFIRMED'):

Constraint Columns On conflict (23P01)
excl_appointment_bay_overlap service_bay_id WITH =, tstzrange(start_time, end_time, '[)') WITH && Retry with the next free pair
excl_appointment_tech_overlap technician_id WITH =, same range Retry with the next free pair
excl_appointment_vehicle_overlap vehicle_id WITH =, same range 409 KUSS_VEHICLE_ALREADY_BOOKED, no retry
  • The [) bounds let 09:00–10:00 and 10:00–11:00 sit back to back.
  • A cancelled row drops out of the partial constraints, so its bay and technician are free at once.
  • service_bay_id, technician_id and vehicle_id are NOT NULL, because NULL never conflicts in an exclusion check.
  • Read index: appointment (dealership_id, start_time, end_time) WHERE status = 'CONFIRMED'.
  • idempotency_key: response_status and response_body stay NULL until the claim commits. The maintenance job deletes rows older than 24 hours.
  • request_audit: PARTITION BY RANGE (occurred_at), PRIMARY KEY (id, occurred_at), a DEFAULT partition, a BRIN index on occurred_at and a B-tree index on request_id.
  • The service layer checks skill qualification and dealership scope; the database does not.
D

Booking write path

  1. Validate the header at the controller. A missing key gives KUSS_IDEMPOTENCY_KEY_MISSING; a key outside [A-Za-z0-9_-]{1,128} gives KUSS_VALIDATION_FAILED.
  2. Run each attempt in its own transaction (TransactionTemplate, 5 s timeout). book() itself is not @Transactional.
  3. Claim the key first. The hash is SHA-256 over canonical fields, so reformatted JSON or an equivalent offset replays.
  4. Run the vehicle EXISTS precheck before capacity. A booked vehicle on a full slot gets KUSS_VEHICLE_ALREADY_BOOKED, not KUSS_NO_CAPACITY.
  5. Pick a random free bay and the qualified technician with the fewest confirmed minutes that local day.
  6. Insert with saveAndFlush on AppointmentRepository (JPA), then store the response in the key row with one conditional UPDATE (IdempotencyKeyRepository.complete) in the same transaction.
  7. On 23P01 for bay or technician, or on 40P01, roll back and start a new attempt. The fresh snapshot sees the winner, so that resource drops out.
  8. A failure such as KUSS_NO_CAPACITY rolls back the claim too, so a retry with the same key runs fresh.
Deadlock root cause (40P01)

PostgreSQL checks an exclusion constraint after it inserts its own index entry. Two concurrent conflicting inserts can each wait on the other transaction. After deadlock_timeout (100 ms) PostgreSQL aborts one with 40P01. Unique B-tree indexes avoid this with speculative insertion, but exclusion constraints do not. The retry loop handles it, and tests never assert zero deadlock retries. deadlock_timeout=100ms is a required setting for every deployment, because the 1.6–3.2 s backoff is sized for it.

  • Backoff: a 40P01 victim waits a random 1.6–3.2 s outside any transaction (3.2–6.4 s after its next deadlock) before it retries.
  • Bounds: no free DB connection (Hikari connection-timeout 3 s in prod), a statement timeout or the 10 s booking deadline gives 503 KUSS_SERVICE_BUSY with Retry-After: 1. The cap of 100 attempts gives 500 KUSS_INTERNAL_ERROR.
  • Metric: scheduler.booking.gist_retries{conflict_type=bay|technician|deadlock}.
E

Availability read path

GET /api/v1/dealerships/{id}/availability?date=YYYY-MM-DD&serviceType=CODE, read-only transaction.

  1. Load the dealership and the active service type. An unknown one gives 404 KUSS_RESOURCE_NOT_FOUND.
  2. Reject a missing or malformed date, or a date beyond today + 90 days, with 400 KUSS_VALIDATION_FAILED.
  3. Build candidate starts in 30-minute steps from opening time, in the dealership time zone. Keep a start only when start + duration ≤ close and the start is not in the past.
  4. Read the active bay ids and the active technician ids that hold the skill.
  5. Read the CONFIRMED appointments that overlap the opening hours in one indexed query.
  6. Sweep in memory: capacity = min(free bays, free qualified technicians) per start. Keep starts with capacity ≥ 1.

Response: {dealershipId, date, serviceTypeCode, timezone, slots: [{startTime, availableCapacity}]}. startTime carries the dealership offset. Booking uses the same candidateStarts list as its only grid and hours check. A timer scheduler.availability.query.duration measures each call.

F

Cancel path

POST /api/v1/appointments/{id}/cancel with Idempotency-Key, in one @Transactional(timeout = 5) call. No explicit locks anywhere.

  1. Claim the key: replay, 422 on a different hash, 409 KUSS_IDEMPOTENCY_IN_FLIGHT on a concurrent claim.
  2. Run one atomic conditional JPQL UPDATE … SET status = 'CANCELLED', cancelled_at = now WHERE id = :id AND status = 'CONFIRMED' AND start_time > now (cancelIfConfirmedAndNotStarted). No read locks the row first; a second canceller waits for the first to commit and matches nothing.
  3. Load the appointment. A missing row gives 404 KUSS_RESOURCE_NOT_FOUND.
  4. Return 409 KUSS_APPOINTMENT_ALREADY_STARTED when the update matched nothing and the row is still CONFIRMED (start_time ≤ now).
  5. Otherwise (cancelled just now, or already CANCELLED) return 200 with the current state.
  6. Store the 200 response in the key row and commit.

The partial constraints release the bay and the technician as soon as the cancel commits.

G

Error codes

Every non-2xx response is RFC 9457 application/problem+json with top-level code and requestId. One SchedulerGlobalHandler maps exceptions from one ErrorCode enum. It also sets the request attribute kuss_error_code for the audit row. No stack trace, class name or SQL reaches detail; a validation error names each invalid field. /error and requests Tomcat rejects before the app also answer with a ProblemDetail and a KUSS_* code (Tomcat-level ones carry no requestId).

Code HTTP Meaning
KUSS_VALIDATION_FAILED 400 Bad body or params: off grid, past, outside hours, beyond 90 days, malformed JSON, bad key format
KUSS_IDEMPOTENCY_KEY_MISSING 400 No Idempotency-Key on book or cancel
KUSS_RESOURCE_NOT_FOUND 404 Unknown dealership, vehicle, service type, appointment or path
KUSS_VEHICLE_ALREADY_BOOKED 409 The vehicle already has an overlapping confirmed booking (precheck or constraint)
KUSS_NO_CAPACITY 409 No free bay and qualified technician pair for the whole duration
KUSS_IDEMPOTENCY_IN_FLIGHT 409 Another request with the same key holds the claim
KUSS_APPOINTMENT_ALREADY_STARTED 409 Cancel of a confirmed appointment at or after its start time
KUSS_IDEMPOTENCY_KEY_MISMATCH 422 Same key, different request hash
KUSS_INTERNAL_ERROR 500 Unhandled error or the booking retry cap; sanitized detail
KUSS_SERVICE_BUSY 503 No free DB connection, a statement timeout, or the 10 s booking deadline, on every endpoint; sent with Retry-After: 1
H

The request_audit lifecycle

  • Scope: every path except /actuator/**, /v3/api-docs/** and /swagger-ui/**, matched on the normalized servlet path. The filter also audits reads, 4xx and 500 responses.
  • Row: status, error_code from kuss_error_code (null on 2xx), duration, method and path truncated to column size.
  • Payload: only for POST /api/v1/appointments, sanitized to the four body fields. The row holds no PII.
  • Isolation: the write runs after the business transaction closes, so a rolled-back 409 or 500 still gets its row. An audit failure never fails the HTTP response.
  • Meter: scheduler.audit.writes{status=success|failure}.

Partition ownership. Flyway V1__create_schema.sql owns the parent table, its PK, its indexes and the DEFAULT partition. MaintenanceService runs the only DDL outside Flyway:

  1. Run at startup in a SmartLifecycle with phase Integer.MIN_VALUE, before the web server listens.
  2. Run daily at 00:05 UTC with @Scheduled.
  3. Create day partitions D to D+7 with CREATE TABLE IF NOT EXISTS … PARTITION OF request_audit.
  4. Drop day partitions older than six months (Period.ofMonths(6)) with DROP TABLE IF EXISTS.
  5. Delete DEFAULT rows older than six months, and idempotency_key rows older than 24 hours.
  6. Catch and log each step at WARN. Every statement is idempotent, so N instances are safe.

Partition names come only from dates or from pg_class names that match ^request_audit_p[0-9]{8}$. The job never alters columns, indexes or constraints, because partitions inherit them from the parent.

KUSS-04 phases, gates and review flow

  1. 01 · 3hProject skeletonWrapper, Spotless + Checkstyle gates, Testcontainers on Podman, compose, Clock bean
  2. 02 · 4hSchema and seedFlyway V1 schema with 3 EXCLUDE constraints, V2 seed (London bay-bound K=3, tech-bound K=2)
  3. 03 · 2hError handlingErrorCode enum, SchedulerGlobalHandler, requestId filter
  4. 04 · 5hAvailability + catalog readsTimeSlotUtils, in-memory sweep, read endpoints
  5. 05 · 6hBooking concurrency + idempotencyClaim-first key, vehicle precheck, whole-tx retry, BookingConcurrencyIT
  6. 06 · 3hAppointment API + OpenAPIBook, cancel, reads over HTTP, springdoc
  7. 07 · 6hObservability and auditAsync audit, partition job, metrics, probes, JSON logs

Order is strict: each phase builds on the one before. Total effort is 29 h.

TDD gate per phase. Write the failing tests first, then make ./mvnw verify green before the next phase starts:

  1. Run spotless:check in validate. It fails on any unformatted Java, POM, SQL, YAML or Markdown file.
  2. Run Checkstyle MethodLength max=20 on the formatted main sources.
  3. Run *Test with Surefire and *IT with Failsafe against real PostgreSQL in Testcontainers.

The two reviewers discuss once through docs/agent-discussion/. Nothing goes to origin before the user approves.
